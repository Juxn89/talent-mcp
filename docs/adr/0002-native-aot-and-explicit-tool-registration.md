# ADR-0002 · Register tools explicitly, never by assembly scan

| | |
|---|---|
| **Status** | Accepted |
| **Date** | 27 Aug 2026 · scope limit added same day |
| **Phase** | F0 (risk spike) |
| **Resolves** | Risk #1 in the plan, *as written*: "Native AOT vs reflection-based discovery" |
| **Does NOT resolve** | Whether Native AOT is achievable for the real host. See [Scope limit](#scope-limit-of-this-experiment) — EF Core is the next gate |

## Context

The plan's decision table commits to Native AOT with a published cold-start benchmark, and names the
matching risk: `WithToolsFromAssembly()` discovers `[McpServerTool]` methods by reflection, so
trimming may break it. The stated fallback cascade was **reflection → explicit registration → JIT +
ADR**, and F0 exists to resolve it *before* F2 writes six tools on top of the wrong foundation.

The plan's own sample code — copied from the SDK docs — uses assembly scanning:

```csharp
builder.Services.AddMcpServer()
    .WithHttpTransport()
    .WithToolsFromAssembly();   // reflection
```

## The experiment

Three configurations of a minimal stdio MCP server (SDK 2.2.0, .NET 10.0.400), each asked for a
real `tools/list` over stdio. Run 27 Aug 2026.

| Config | Registration | Trimming | `tools/list` result |
|---|---|---|---|
| **C** (control) | `WithToolsFromAssembly()` | none | ✅ returns `extract_skills` with a generated `inputSchema` |
| **A** | `WithToolsFromAssembly()` | `TrimMode=full` | ❌ `-32601 Method 'tools/list' is not available.` |
| **B** | `WithTools<SkillTool>()` | `TrimMode=full` | ✅ returns `extract_skills` with a generated `inputSchema` |

Static analysis agreed, at both the Roslyn analyzer level and full-graph ILLink:

| Config | IL warnings (analyzers) | IL warnings (ILLink, `TrimMode=full`) |
|---|---|---|
| A | 2 × `IL2026` | 2 × `IL2026` |
| B | 0 | **0** |

The SDK annotates the reflection path itself and names the fix:

> `IL2026`: Using member `McpServerBuilderExtensions.WithToolsFromAssembly(...)` which has
> `RequiresUnreferencedCodeAttribute` can break functionality when trimming application code. **The
> non-generic WithTools and WithToolsFromAssembly methods require dynamic lookup of method metadata
> and might not work in Native AOT. Use the generic WithTools method instead.**

**The failure mode is the important part: it is silent.** Config A starts cleanly, logs
"Application started", accepts the connection and then reports that `tools/list` is *not a method*.
The tools capability simply is not advertised. Nothing crashes, nothing logs an error, and a
smoke test that only checks "does the server start" passes. A server with zero tools would have
shipped.

## Decision

**Register every tool explicitly with the generic `WithTools<T>()`. Never use
`WithToolsFromAssembly()`, in any host, including tests.**

The plan's fallback cascade resolves at step 2: explicit registration, not JIT. This removes
reflection-based discovery as an obstacle to AOT at a cost of one line per tool type — and it is
worth doing on its own merits (deterministic ordering, a trim-clean build) regardless of whether
AOT ever ships.

It does **not** establish that Native AOT is achievable. See the scope limit below.

A consequence that constrains F2's code: **`WithTools<T>()` rejects static classes** with
`CS0718: static types cannot be used as type arguments`. The plan's `public static class EchoTool`
sample cannot be used. Every `[McpServerToolType]` class must be non-static — `sealed class` with
static tool methods works and is the shape to follow.

```csharp
builder.Services.AddMcpServer()
    .WithHttpTransport(o => o.SessionMode = HttpServerSessionMode.Stateless)  // ADR-0001
    .WithTools<SearchJobsTool>()
    .WithTools<GetJobTool>()
    .WithTools<ExtractSkillsTool>()
    .WithTools<ScoreCandidateFitTool>()
    .WithTools<RejectCandidateTool>()
    .WithTools<BulkScoreShortlistTool>();

[McpServerToolType]
public sealed class ExtractSkillsTool   // NOT static
{
    [McpServerTool(Name = Mcp.ToolNames.ExtractSkills), Description("…")]
    public static ExtractSkillsResult Execute(string text) => …;
}
```

Explicit registration also buys the deterministic tool ordering the revision asks for: the
registration order is the source of truth, rather than whatever order reflection happens to
enumerate members in.

## Two incidental findings worth keeping

**Tool names are derived from the method name, snake-cased.** `ExtractSkills()` was published on
the wire as `extract_skills` with no attribute argument. Convenient, and a trap for the
no-magic-strings policy: a C# rename would silently change the protocol contract. **Always set
`[McpServerTool(Name = Mcp.ToolNames.X)]` explicitly** so the wire name is pinned to the constant
and a refactor cannot move it.

**`inputSchema` is generated by the SDK, not hand-written.** Config B and C both emitted
`{"type":"object","properties":{"text":{"type":"string"}},"required":["text"]}` from the method
signature alone. The revision's "`inputSchema` is mandatory" requirement is satisfied by using the
attributes correctly; the conformance test asserts its presence, it does not author it.

## Scope limit of this experiment

**The spike measured a minimal dependency graph, not the real one.** All three configurations were
the MCP SDK plus the generic host and nothing else — no EF Core, no Npgsql, no OpenTelemetry, no
OAuth. That was the right shape for isolating the question the plan asked, and it is the wrong shape
for concluding anything about the shipped host.

**The likely next blocker is EF Core, and it is a bigger one than reflection-based discovery was.**
EF Core is not AOT-compatible: it builds its model at runtime. The supported route is *compiled
models*, generated to C# at build time by a CLI tool so the model is static
([ASP.NET Core Native AOT docs](https://learn.microsoft.com/en-us/aspnet/core/fundamentals/native-aot?view=aspnetcore-10.0),
[State of Native AOT in .NET 10](https://code.soundaranbu.com/state-of-nativeaot-net10)) — verified
27 Aug 2026. Npgsql, OpenTelemetry and the OAuth stack are each unverified for AOT here too.

Two things follow, and both matter more than installing a linker:

1. **A design question for F1/F2 that AOT depends on:** does `Talent.Mcp.Server.Stdio` need EF Core
   at all? If the stdio host reaches Postgres directly, AOT hinges on compiled models. If instead
   the stdio host is a thin client — or the tools that need data are only served over HTTP — the AOT
   target shrinks to something plausible. **Decide this with the code in front of you, not now.**
2. **Trim-clean is necessary, not sufficient.** Zero `IL2026`/`IL3050` at analyzer and ILLink level
   says nothing about runtime reflection that AOT forbids outright. Config A is exactly that lesson:
   static analysis and runtime disagreed in *direction* — it warned, and the runtime failure was
   silent rather than loud.

So: the reflection obstacle is gone and the registration decision is made and permanent. Whether
the AOT goal in the plan's decision table survives contact with EF Core is **an open question for
F6**, and the plan's cut order already lists AOT first if scope has to give.

## Cold start: baseline recorded, native number deferred

**Native AOT could not be linked on this machine.** MSVC is present
(`VS 18 Insiders, MSVC 14.51.36231`) but the Windows SDK is not, so ILCompiler fails with
`error: Platform linker not found`. The trim/AOT *analysis* above does not need the linker and is
unaffected — but there is no native binary and therefore no honest native cold-start number.

Baseline for F6 to compare against, measured on the trimmed self-contained JIT build (10 runs, 2
discarded as warm-up, process start → exit with stdin closed immediately):

| Metric | Config A | Config B |
|---|---|---|
| Cold start, median | ~646 ms | ~682 ms |
| Cold start, min–max | 519–923 ms | 593–713 ms |
| Publish dir, self-contained untrimmed | 80.7 MB | — |
| Publish dir, self-contained `TrimMode=full` | 22.7 MB | 22.7 MB |

A and B are indistinguishable at this sample size, which is the expected result — runtime
initialisation dominates, not the discovery mechanism. So **choosing explicit registration costs
nothing at startup either**; it is not a speed/convenience trade, just the correct call.

**F6 measures this in CI or inside the multi-stage Docker build that F5 needs anyway** — not on a
developer laptop. A cold-start number in the README has to be reproducible, and one produced by a
single machine's toolchain is not. Installing the local C++ workload is optional convenience, not a
prerequisite; and per the scope limit, it should not be done before the host's real dependency graph
exists, or the number will describe a server that cannot reach a database.

Until then **no cold-start claim goes in the README.**

## Consequences

- F2 writes six tools with explicit registration and non-static tool types from the first commit.
- The `Talent.Mcp.Server.Stdio` host — the one launched per session as a `dotnet tool`, where cold
  start actually matters — keeps `PublishAot=true` as a goal that is no longer blocked *by tool
  discovery*. Its remaining gate is the data-access dependency; see the scope limit.
- Add a **conformance test asserting `tools/list` returns all six tools by name**. That test is what
  would have caught config A's silent emptiness, and it is cheap. A test that only asserts the
  server starts is worthless here.
- CI should publish trimmed at least once so `IL2026`/`IL3050` regressions surface at merge time
  rather than at release. With `TreatWarningsAsErrors=true` a reintroduced assembly scan fails the
  build.

## Reproduction

Not committed to the repo — F6 rebuilds it against the real host. To redo:

1. Minimal `net10.0` console project, `ModelContextProtocol` 2.2.0 +
   `Microsoft.Extensions.Hosting` 10.0.11, `PublishAot=true`, `RuntimeIdentifier=win-x64`,
   `TrimmerSingleWarn=false`, `EnableTrimAnalyzer/EnableAotAnalyzer=true`.
2. One `[McpServerToolType] sealed class` with one `[McpServerTool]` method.
3. **Send logging to stderr** — see the note below, or the JSON-RPC stream is unreadable.
4. `dotnet publish -p:PublishAot=false -p:PublishTrimmed=true -p:SelfContained=true
   -p:TrimMode=full` for the trim analysis without needing the native linker.
5. Pipe `{"jsonrpc":"2.0","id":1,"method":"tools/list"}` to stdin and read the first stdout line.

> **Trap hit while running this spike:** `Host.CreateApplicationBuilder` installs a console logger
> that writes to **stdout**, which corrupts the JSON-RPC stream — the first "response" was a log
> line. A stdio host must do
> `builder.Logging.ClearProviders(); builder.Logging.AddConsole(o => o.LogToStandardErrorThreshold = LogLevel.Trace);`
> This is why the plan says stderr for stdio hosts. It is not a style preference; the transport
> breaks without it.
